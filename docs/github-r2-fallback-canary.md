# GitHub / R2 registry-fallback canary

This repository proves that `zed install --frozen` still materializes a
package when the HTTP registry is down, as long as the packed tarball is at a
guessable public CDN key (`packages/{org}/{name}/{version}/…` or
`github/{owner}/{repo}/{tag}/…`). That is the `cdn.zpkg.net` contract.

The canary is credential-free and uses only loopback HTTP:

1. publish a disposable package to a `file://` registry;
2. copy the tarball onto the guessable CDN layout;
3. install once so a lock exists, then uninstall and drop the store;
4. point `--registry` at a closed `127.0.0.1` port;
5. set `ZED_PKG_SOURCE_FALLBACK_ALLOW_LOOPBACK=true` (production loopback stays
   hermetic) and `--r2-public-base http://127.0.0.1:<cdn>`;
6. `zed install --frozen` must restore the packed payload from the CDN mock.

It also round-trips the `get_version` JSON call/receipt frame over TCP NDJSON,
using the same key as `zed-interfaces/route-maps/zed-api.route-map.json`
(generated by `github.com/oresoftware/api-docs`). zed-cli itself still speaks
HTTP; the TCP check is the typed RPC wire, not a second CLI transport.

When the TypeScript copies are passed in, the generated `zed-clients` routes
file must match `zed-interfaces/generated/typescript/zed_api.ts` (banner
comments excluded).

## Local run

From a sibling checkout of `zed-pkg`:

```bash
cargo build --release --manifest-path ../zed-pkg/zed-cli/Cargo.toml --bin zed
python3 scripts/github_r2_fallback.py \
  --zed ../zed-pkg/zed-cli/target/release/zed \
  --work-root /tmp/zed-github-r2-fallback \
  --route-map ../zed-pkg/zed-interfaces/route-maps/zed-api.route-map.json \
  --interfaces-generated-ts ../zed-pkg/zed-interfaces/generated/typescript/zed_api.ts \
  --clients-generated-ts ../zed-pkg/zed-clients/clients/typescript/src/generated/zed-api.routes.ts
```

The work root must not already exist.
